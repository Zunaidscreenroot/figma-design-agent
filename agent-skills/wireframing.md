# Polished UX Screen Design

## Objective

In this product, "wireframe" means a polished, review-ready UX screen — not a generic low-fidelity grayscale sketch. Produce editable Figma screens that look intentionally composed by a senior product designer and are grounded in the actual product context.

## Before designing

1. Identify the primary user, their main task, success outcome and important constraints.
2. Inspect selected/reference frames, existing components, variables, typography, spacing, naming and layout patterns.
3. Identify the screen archetype and retrieve evidence from similar accepted examples. Match by task and domain, not just visual resemblance.
4. Establish the information hierarchy, content density, primary/secondary actions and relevant states before adding visual detail.
5. Distinguish explicit requirements from assumptions. Never invent business rules or component IDs.

## Composition rules

- Reuse existing components and tokens when evidence supports them.
- Prefer native editable nodes and Auto Layout where appropriate.
- Use realistic, specific copy and meaningful values rather than lorem ipsum or generic placeholder boxes.
- Make spacing rhythm, proportions, alignment, typography and visual grouping purposeful.
- Match density to the job: operational, financial and geospatial screens often need efficient, information-rich layouts rather than oversized marketing sections.
- Make the primary action obvious and place it where the workflow naturally requires it.
- Include validation, disabled, loading, empty, error, success and consent states when relevant.
- Respect the current product's visual language; don't introduce a new palette, font, radius system or component style without evidence.
- If no design system is available, choose a restrained, coherent direction and mark it as provisional.

## Anti-generic quality gate

Do not default to:
- repeated rounded cards around every piece of content
- arbitrary gradients, glow effects or decorative pills
- oversized hero areas unrelated to the user's task
- excessive whitespace that hides useful information
- generic SaaS-dashboard layouts for domain-specific workflows
- vague CTA labels, fake data that conflicts with the task, or placeholder copy
- making every screen in a flow look like the same template

These patterns are not categorically forbidden; use them only when the user task, evidence or visual hierarchy warrants them.

## Verification

1. Confirm every required field, decision point, content section and state exists.
2. Check component reuse, token usage, Auto Layout and responsive constraints.
3. Inspect the rendered screenshot for hierarchy, spacing, alignment, clipping, overlap, weak contrast and generic composition.
4. Fix objective defects before finishing; keep repair attempts bounded.
5. Treat accepted examples as references, not universal templates.
6. Save reviewer corrections as scoped lessons. Promote a preference to a reusable rule only when the user explicitly approves it or repeated evidence supports it.

## Output

Return an editable, polished Figma composition with realistic content and a concise note of assumptions. Do not deliver a static screenshot in place of the actual design.
