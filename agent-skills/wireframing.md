# Polished UX Wireframing Skill

## Definition
For this product, a wireframe means a polished, review-ready UX screen. It is not a black-and-white low-fidelity skeleton. Output should feel authored by a senior product designer and remain fully editable in Figma.

## Procedure
1. Understand the primary user task, outcome, decision and action.
2. Inspect relevant approved screens, actual component data and tokens before choosing a layout.
3. Select a screen pattern appropriate to the domain. Retrieve by task similarity, not just visual similarity.
4. Establish hierarchy and content density before decoration.
5. Use realistic product-specific content and plausible values. Avoid generic placeholders.
6. Reuse compatible components and variables.
7. Use intentional spacing rhythm, type hierarchy, alignment and purposeful grouping.
8. Use Auto Layout for predictable responsive relationships when possible.
9. Include relevant validation, loading, empty, success and error states.
10. Produce native editable Figma elements, not a flattened image.
11. Re-inspect the generated frame and compare its screenshot with the brief and references.
12. Repair defects and record unresolved assumptions.

## Anti-generic rules
- Do not wrap every section in a card by default.
- Do not add oversized hero areas, gradients, decorative blobs, arbitrary icons or excessive rounded corners without a product reason.
- Do not use generic dashboard compositions for unrelated tasks.
- Do not use Lorem ipsum, “Title here”, “Description goes here”, “Sample text”, or placeholder values in final output.
- Do not invent a new visual system when a project system is available.
- Do not copy a reference layout blindly if its information architecture does not fit the task.

## Quality checklist
Check primary action clarity, scanability, content density, realistic labels and states, spacing/typography consistency, component/token reuse, edge cases and editability. Use low-fidelity output only when the user explicitly requests it.
